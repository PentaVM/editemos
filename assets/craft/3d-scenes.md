# 3D scenes

Two routes, both from code:

- **Blender, headless.** For film-like scenes, many objects, real lighting. Blender 4.x LTS
  with Eevee (Next); Cycles was about 10x slower with no visible gain for a deadline.
- **In the browser** (Three.js, OGL, Rapier). For product shots, abstract scenes, anything that
  lives next to HTML graphics and must render in the same editemos scene, with alpha.

## Blender from code

1. **The `.blend` is generated entirely by a `build` script**: materials, props, cameras,
   lights, edit. Nothing edited by hand that a build would overwrite.
2. **One Blender process per scene** (`blender -b file.blend --scene S04 ...`). In one process
   for all scenes, animation is not evaluated correctly headless.
3. **Never stack coplanar planes** (flicker, z-fighting). Terrain variation goes into the
   shader or a single mesh.
4. **Dense population with cheap instances** (Geometry Nodes instancing simple shapes) rather
   than a few detailed models. Tens of thousands of trees fit in little memory. No empty strip
   at the horizon: fade it into fog.
5. **Props fill the frame, with real proportions.** Any text or logo on geometry is checked
   zoomed in on a still (an "A" came out solid).
6. **Find every appearance of the brand** (3D, textures, the recorded app, the page) before
   rendering a new logo.
7. **Positions of objects that cross screens are computed from the final camera**, not by eye.
8. **Objects that travel as a group leave together.** Rows spaced more than an object's height;
   under a tilted camera, raised objects look higher on screen, so leave extra room. Fixed
   labels out of the path of moving objects.
9. **In scenes with screens, glare with a high threshold** (1.2 to 4.0) or none: bloom washes
   out the interface.

## Screens inside a 3D scene

- **Three variants per screen:** `preview` (placeholder), `clean` (switched off) and `insert`
  (the real video, through a View Layer). Never simulate the interface in 3D.
- **A Cryptomatte mask per screen object**: a per-frame mask that already respects occlusion.
- **Corner pins per frame** in JSON/CSV (and a `.jsx` for After Effects if a designer needs it).
- **Validate each quad before pasting**: convex, with corners near the frame. A screen behind
  the camera projects corners thousands of pixels away; its polygon pasted the image over
  another screen's mask and a black rectangle appeared.
- **Read the videos one frame at a time** through an ffmpeg pipe and write the result to
  another pipe. Loading whole scenes into memory exhausts it.
- **A screen that appears in another scene gets its own recording**, suffixed `__S04`.

## Control stills, then the render

- Stills at 1280x720, 16 samples, at the start, middle and end of each scene, on one contact
  sheet (0.5-0.9 s each on an RTX 3070). See `frame-review`.
- A legibility test per scene with a screen, at final resolution and colour transform.
- Intermediates lossless; **a changed scene gets a new frame folder** (renders skip existing
  PNGs and would reuse stale ones).

## Distributed rendering

- **GPU watchdog always on**, on every machine: pause at 90 °C, resume at 78 °C, and pause when
  there is no reading. A desktop RTX 3070 reached 84-87 °C; another machine rebooted twice under
  sustained load until it got a rest between frames.
- **An agent with a task queue from day one**, not loose scripts sent by chat: one script per
  person, the remote side configures nothing, the first task is always a diagnosis (disks, GPU,
  temperature, create/rename/delete in the work folder), and the agent picks the disk with the
  most space (Blender and temp files included).
- **Several workers per GPU on one queue.** With 8 GB of VRAM two Eevee 1080p renders fit.
  Scenes are claimed with an atomic `mkdir`; the host takes the queue from the front, the remote
  from the back; scenes with screens first.
- **Upload is the bottleneck** (~1 MB/s at home: 9 minutes for 556 MB). Give the remote machine
  the light scenes, or have it compress to high-quality H.264 before uploading when the
  destination is 1080p.
- **Machines in different houses:** a mesh VPN (Tailscale) plus OpenSSH/SFTP into a jailed
  folder, without opening the router. Auth keys read from the clipboard, never the chat;
  ephemeral, or reusable with a 7-day expiry if the remote may reboot. Revoke them at the end.
- **PowerShell traps:** no function named after an executable (a `Sftp` function called itself
  and printed a false "connection OK"); test the real path (same binary, same key, same IP);
  set ACLs by SID or `PC\user`, never a bare name (user `Penta` and PC `PENTA` were confused);
  when installing OpenSSH server, fix the permissions of `ssh_host_*_key` before starting it.

## In the browser

An editemos scene is a page seeked to each frame, possibly by several browser windows at once,
in any order. Any 3D library works if the frame is a pure function of time:

- **Three.js:** `new THREE.WebGLRenderer({ alpha: true, preserveDrawingBuffer: true })`, no
  animation loop; in `render(frame)` set the camera and objects, then `renderer.render(scene, camera)`.
- **OGL:** the same for custom shaders: a `uTime` uniform from the frame, one draw per seek.
- **Rapier (3D) / Matter.js (2D) physics:** simulation is stateful, so step it from frame 0
  with a fixed timestep (`world.timestep = 1 / fps`; `Engine.update(engine, 1000 / fps)`) once at
  load, store every body's transform per frame, and in `render(frame)` only read the stored
  frame. Same inputs, same version: same result in every worker.
- **glTF Transform:** optimise models before loading them
  (`npx @gltf-transform/cli optimize in.glb out.glb`): smaller files, faster scene load per
  worker.
- **Mount after loading.** Load models and textures first (`await loader.loadAsync(...)`), then
  call `Motion.composition(...)`: the renderer waits for the scene to mount (up to 10 s) before
  it seeks the first frame.
- Vendor the library next to the scene (a local `.js` file): scenes open from disk, and a CDN is
  one more thing that can fail during a render.
